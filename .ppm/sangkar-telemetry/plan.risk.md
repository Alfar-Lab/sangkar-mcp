# Risks and open questions

## Risks

| Risk | Mitigation |
|---|---|
| **The recorder becomes a latency tax on every tool call.** Measuring `JSON.stringify(envelope)` doubles the serialisation the transport already does (`src/index.ts:427`). | The measurement is one `JSON.stringify` per call on an answer that is already ≤ 32 000 tokens (`budget.ts` `MAX_BUDGET_TOKENS`), and the write is buffered, so no syscall happens on the hot path. If a phase_1 or phase_3 run shows a regression, the fallback is to record `payload_tokens` from `Buffer.byteLength` of the already-rendered text in `answer()`/`renderEnvelope` instead of re-serialising — a one-line change at the same call site, not a redesign. |
| **A telemetry bug breaks the product.** A thrown sink, a full disk, an unwritable data dir. | Every sink call is wrapped; the first failure logs one `warn` and disables the process's sink, so the failure is visible once and never again, and `recordCall` cannot throw into the handler's `finally`. A test feeds a throwing sink and asserts `recordCall` returns and exactly one `warn` was logged. |
| **A private value leaks into a record through prose, not through a spread.** The obvious regression is someone spreading `payload` or `args` "to be helpful" — but the audit's counter-example needs no spread at all: `trace` builds `stale_reason` as `"${node.path}" has no indexed file row` / `… was last written by generation N` (`src/tools/trace/handler.ts:682-683`), `status` composes verdict prose (`status/handler.ts:252,298,303`), `search` writes a sentence with counts (`search/handler.ts:221`), and `expand`, `index` and `summary` write fixed sentences (`expand/handler.ts:539`; `index/handler.ts:282,291`; `summary/handler.ts:658,685`) — six tools in all, and `src/shared/envelope.ts:51` types the field as plain `string`. Copying the envelope field verbatim would put a repo path and a basename in every stale `call` record. | Two rules instead of one: the builders copy an explicit whitelist, **and** `stale_reason` is mapped to a closed enum — the five `STALE_REASONS` values plus `"other"` — so prose cannot survive even when a handler writes it. `tests/telemetry.test.ts` serialises a record built from a real repo path, a real symbol name and a `search.query`, deep-walks every value of the parsed line, and asserts none of the three appears; a second case builds a `call` record from an envelope carrying the `trace` wording and asserts `stale_reason: "other"` with neither the path, its basename nor the word `generation` in any value. `arg_names_set`, `result_counts`, `nodes_by_kind` and `edges_by_kind_tier` are the only "dynamic-shape" fields, and every one is a name, a length or a closed-union key. |
| **The report is not actually self-contained** because an inline `<script>` could require a runtime, or a string could close the tag. | No framework: plain DOM calls in one inline script. The JSON blob escapes `<` to `\u003c`, all strings go through `escapeHtml`, and `tests/telemetry-report.test.ts` asserts the rendered file contains no `http://`, `https://`, `src=`, `<link`, `@import` or `url(`. |
| **`repo_size_bucket` measures the graph, not the repo.** A first-ever process sees no graph and records `none`. | Deliberate: bucketing the real file count needs a walk, and the only walker is `src/indexer/discover.ts`, which `shared-isolation` forbids telemetry from importing. The field is documented in `TELEMETRY.md` as the published graph's byte-size bucket, and `index_run.files_seen` carries the real count for any process that indexed. |
| **`session.languages` is empty for mcp/cli.** It is `[]` unless the process walked the tree. | Documented, and the run-level truth (`index_run.languages`) is populated from `discovered.files`. A walk on every server start was rejected as a startup latency regression. |
| **Racing install-id rotation.** A server and a worker starting on the same day, or a rotation on the first start of a new day, can both write `install_id.json`. | Create with flag `wx` and fall back to reading on `EEXIST`; the worst case is two processes holding different ids for the same day, which only splits one day's rows into two install ids. Nothing in a record set depends on global agreement. |
| **Two phases touching one file.** | The plan is file-disjoint by construction: `src/index.ts` and `src/shared/cli/args.ts` belong to phase_1 only, `bin/sangkar.ts` to phase_2 only (see plan.approach.md §Design 7 for the rejected alternative), `src/shared/*` split between phase_0 (`record`, `sink`, `identity`, `telemetry`, `config`) and phase_2 (`report`, `html`, `cli`). Two named exceptions, both serial and both recorded rather than hidden: phase_3 adds one clause to `bin/sangkar.ts`'s `USAGE` line and, in `README.md` (a file no other phase owns), one row plus the sentence above the table that counts the rows — the prose says "Two settings" and a bare row would contradict it (TASK-019), which is the only way the consent disclosure reaches the file a user reads without putting the bin in a third phase's parallel lane. |
| **Two processes append the same daily file.** The server and the worker it spawns each hold a recorder, and `src/tools/index/handler.ts:155` passes the whole parent environment, so both write `<dataDir>/telemetry/<date>.jsonl` concurrently. | One append per flush: the buffer is joined with `\n` and capped at `FLUSH_AT_RECORDS` (32) records, so each `appendFileSync` is a single `O_APPEND` write and interleaving happens at line boundaries only. A torn final line from a killed process is not a corruption: `readRecords`' skip rule counts it as `unparsed`, and `tests/telemetry-report.test.ts` pins that path. A lock was rejected — it would make a lost record into a failed tool call. |
| **Existing suites start writing telemetry into their fixtures** because it is on by default. | Verified safe: the spawn-based suites pass a temp `--data-dir` (`tests/mcp-surface.test.ts:105-141`), and the suites that assert an **exact** data-dir listing (`tests/publish.test.ts:127,155,200,291,342` and `tests/smoke.test.ts:260`, each `toEqual(["graph.db"])`) build the store through the publish primitives in process with no telemetry instance. Telemetry is created only by `main`, so nothing appears under them. `tests/worker.test.ts:141-144` is a `readdir` + `.stage.` filter, not an exactness assertion, so it is not evidence either way. |
| **A buffered tail is lost on `SIGKILL`.** | Accepted and documented: at most 32 records or 5 s of records. The graceful paths (SIGINT, SIGTERM, stdin EOF, worker `finally`, one-shot CLI exit) all flush. |
| **`SANGKAR_TELEMETRY=off` silently stays on in a child process** (the server spawns the worker with `{...process.env}`, `src/tools/index/handler.ts:155`). | Verified: the child inherits the whole parent environment, so `off` propagates to the worker without a new flag. The phase_1 integration test asserts the off case through the spawn path, not through an injected config. |
| **Unbounded growth of `telemetry/*.jsonl`.** | Out of scope by decision: no pruning in this plan. Files live under `.sangkar/` (ignored, content `*`), a day is one file, and a corrupted or oversized file is skipped with a count rather than read into memory unbounded — `readRecords` reads line by line. |

## Open questions

| Question | Blocking? | Who answers |
|---|---|---|
| Should `sangkar telemetry` also print a short summary to stdout (one line: path + record count), or write the file silently? | **No** — the plan fixes it: one line, mirroring `runTool`'s "stdout is the answer" rule. A silent verb is worse for a shell user. | user, if they want it silent |
| Which percentile definition for `p50`/`p95`? | **No** — nearest-rank on the sorted sample (`sorted[min(n-1, ceil(q*n)-1)]`), stated in the task packet so the test and the renderer cannot disagree. | user, only if they want interpolation |
| Should the report embed the `install_id` values it saw? | **No** — the report shows counts only (`install_ids_seen`), because a random 32-hex id is useless to a human and is the one identifier the whole design is built to keep out of sight. | user, if they want them |
| Is a "no records in range" invocation an error or an empty report? | **No** — it writes the report with an empty-state panel and exits 0; the verb's job is producing a file. `--since` with a malformed value is the only usage error (exit 2, no file). | user, if they want a non-zero exit |
| Retention/pruning of old `.jsonl` files | **No** — explicitly out of scope; a future verb or the report's own `--since` handles it. | user, post-MVP |
| A remote sink | **No** — the interface exists (`TelemetrySink`) so it is additive, but no plan phase builds one. | user, post-MVP |
