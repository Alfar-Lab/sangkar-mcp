# Risks and open questions

## Risks

| Risk | Mitigation |
|---|---|
| **#1 a server started before the first index never serves the graph.** The absent store variant has no connection, so a refresh keyed on the store's kind would leave `bootstrapping` as the answer for the process's whole life — the exact failure #1 names, in the flow "run `sangkar index` while the server is up, then `status`". | The refresh decides from the file, not from the store variant: `absent` + a present file builds a ready store. TASK-005 test (e) covers absent → ready explicitly; TASK-004's "bootstrapping is unchanged" assertion is about an empty data dir, not about never refreshing. |
| **#1 swap invalidates in-flight state.** Cursors minted under the previous generation must not become valid again, and `pendingCalls` may have a handler between `begin()` and `end()` when the fingerprint changes. | Refresh happens in `callTool` *before* dispatch, and every handler is synchronous sqlite work, so no handler is mid-query. The generation-bound cursor check is the existing guard; TASK-005 test (d) asserts a pre-swap cursor is refused after the swap. |
| **#1 a broken newer file disables the server.** A publish that lands with a newer schema version, or a different `project_root`, would be opened by `refresh` and could refuse the session mid-life. | Re-run the same guards `openStore` runs (`readSchemaVersion`, `guardRoot`) inside `refresh`; on any failure keep the previous reader, keep answering, and set `stale_reason` so the answer says why. The handle is closed only after the replacement is fully built. |
| **#1 `status.health.statement_cache_entries` reads the wrong handle.** After a swap, the per-connection cache belongs to the new handle; a stale reference would report the old one. | The reader is rebuilt with the connection and the whole `ToolContext` is replaced, never mutated in place; the phase gate's `status` probe asserts the entries exist rather than a fixed number. |
| **#6 better binding moves count bands.** `tests/parser-parity.test.ts` asserts unresolved rows within 15 % of CRG's 44 338 and leaves `imports` recorded-not-asserted; `tests/acceptance.test.ts` picks "a parsed, unresolved-free file" by SQL and asserts `eq` legality on it. | Both run in the phase 1 gate. A within-band move is expected and must be reported as such; the `imports` oracle is not gated, so no assertion is weakened. `tests/index-integration.test.ts` only asserts `unresolved > 0`. |
| **#6 `..` collapse resolves outside the tree.** `resolveFrom` on `../../../../etc/passwd` would produce an escaping stem. | The helper returns `null` for a path that escapes the root, and `moduleCandidates` then falls back to today's repo-wide match, which can only name files that are in the index. A test covers the escape case. |
| **#7 `git status` is a second git contract with different rules.** `--relative` and `--no-ext-diff` are rejected by `status`; porcelain paths are toplevel-relative; without `--untracked-files=all` a whole untracked directory collapses to one `dir/` row. | One bounded spawn with the accepted prologue, `-uall`, and a `rev-parse --show-prefix` step for a sub-directory root; a git failure degrades to today's behaviour (`degraded: true`) instead of throwing, exactly like `gitNameStatus`. Fixtures cover a sub-directory root and an untracked directory with two files. |
| **#7 `summary` has no `unmatched_files`.** The repro's `unmatched_files: null` came from `impact`; `summary` never had the field, and adding it would be a second contract change in one task. | Scope decision: the change set gains the state; `summary`'s payload is extended only if `TOOLS-SPEC` §4 documents such a field. Otherwise `summary.patch` shows the untracked row and the field question is filed, not improvised. |
| **#4 `status` with no paths now lists up to 107 rows** and the default budget is 800 tokens, so every default `status` call could come back `truncated: true`. | That is the honest shape and the test asserts it (`truncated: true`, `not_indexed_total: 107`, `not_indexed.length < 107`, `not_indexed_total === coverage.skipped`), not a fixed list. If the truncation proves noisy in the gate, the accepted alternative is a smaller default list with the same total, which the same assertion allows. |
| **#8 exact-shape assertions break.** `tests/mcp-surface.test.ts:230,232,245` use `toEqual` on properties that gain a description or an example. | The closing task of phase 2 changes those three assertions to `toMatchObject` and adds the invariant "every property has an enum or a description, every tool has an example". Both the contract and the assertion move, and the commit body says so. |
| **Payload churn is public.** `decisive`, `coverage.tests`, `totals.not_indexed_total`, `ChangeState: "untracked"` are all consumer-visible in a 0.1.0 beta. | All land behind `TOOLS-SPEC` updates in the same phase, and the phase commits use `!` (behaviour/payload change). `docs/INSTRUCTIONS.md` stays byte-identical, so the agent-facing prompt does not drift. |
| **#7 the change set and freshness disagree.** Untracked entries live in `entries`, while `drift` is computed from `changed + removed` (`src/tools/summary/handler.ts:816`), so a tree could report `stale: false` beside a change set that just grew. | TASK-009's contract makes an untracked path count as drift, and its test asserts `changed_files_total: 2` with `stale` telling the same story. The four-state pin at `tests/tools-smoke.test.ts:592` is in that task's `files`, so the fixture cannot silently disagree. |
| **#9 item 1 is called "shipped" while `health.indexer` can never say `running`.** `freshness.ts:54` lists `BUSY_INDEXER_STATES` and `reader.ts:86` advertises `idle | running | failed`, but nothing writes the busy values. | Out of scope with a stated reason: writing them needs a child-liveness protocol (the server claiming a worker is alive), which no open issue requires after validation. "Items 1, 3, 4 shipped" refers to the identity keys, not to the indexer state. |
| **Docs trail behaviour by one phase.** Phase 1 does not touch manifests; §1/§2/§4 are updated in phase 1 and the argument tables in phase 2. | Deliberate: one writer per hotspot file per phase. The phase 1 doc task covers every payload key phase 1 moved; nothing else waits. |
| **The repository's own store is stale** (`g-d975f0` at base `a4ccf52`, 94 files vs 108). Manual probes against it would report pre-fix numbers. | Every manual probe during execution uses a scratch `--data-dir`; re-indexing `.sangkar/graph.db` is a separate orchestrator decision. |

## Open questions

- **#9 item 2 (compact `read_status`)** — resolved as decision D8: record it, do not build it. Not
  blocking. **Ask**: if a compact form is actually wanted, add a task and the measurement that
  justifies it (tokens per answer across a six-call chain); do not start from "the envelope is
  verbose".
- **#7 `summary.unmatched_files`** — whether the field should exist in `summary` is left to the task
  that reads `TOOLS-SPEC` §4. Not blocking; the untracked state is the issue's acceptance criterion
  and does not depend on it.
- **#9 item 1's `health.indexer` values** — `running`/`busy` are read by
  `src/shared/domain/freshness.ts:54` and written by nothing. Writing them needs a second writer
  protocol (the server claiming a child is alive), which is out of scope here. Not blocking: it is
  not part of any open issue's scope after validation.
- **Whether to re-index `.sangkar/graph.db` after the merge** — housekeeping, not part of the plan.
  Blocking nobody; the orchestrator asks before doing it.
